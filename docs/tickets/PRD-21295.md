## Product design

### Goals / Non-goals

**Goals** (v1, user-visible via MCP `tools/list` / `tools/call` through the Agent platform gateway):

- An agent holding a tenant's Airtable Personal Access Token (or an externally-obtained OAuth access token used the same way) can, through MSPbots MCP tools, discover which bases it can access, read a base's table/field schema, list and filter records, fetch a single record, and create, update, or delete records.
- Every tool call is scoped to the credential passed on that one request; two tenants calling concurrently never see or affect each other's data or credentials.
- Failures from Airtable (missing/invalid credential, not found, rate limited, Airtable outage) come back as one consistent, structured error shape instead of raw Airtable error bodies or a 500.

**Non-goals** (explicitly out of scope for v1; see "Decisions made by DEV01" for why):

- Record comments (`data.recordComments:*` scope).
- Webhooks (`webhook:manage` scope) — stateful subscription semantics don't fit a stateless per-request service.
- Schema writes: creating/altering/deleting tables, fields, or views (`schema.bases:write`).
- Attachment upload flows beyond passing through whatever cell value Airtable's API accepts.
- Enterprise/admin scopes (SCIM, audit logs, workspace management).
- Performing the OAuth authorization-code exchange ourselves — the server accepts a bearer-style token from the request header, obtained however the tenant obtained it.
- Airtable's "Sync API" / CSV import endpoints and the `performUpsert` variant of update.

### Acceptance criteria AC1..AC11

- **AC1**: Given a request carries a valid Airtable credential in the `X-Airtable-Api-Key` header, When the agent calls `airtable_list_bases`, Then the response lists the bases that credential can access (`id`, `name`, `permissionLevel` per base; wiki: not covered, source: Airtable API docs `api/list-bases.md`, fetched 2026-11-02), paginating via `offset` if there are more than one page.
- **AC2**: Given a `baseId`, When the agent calls `airtable_list_tables`, Then the response lists that base's tables with each table's `id`, `name`, `primaryFieldId`, and fields (`id`, `name`, `type`) (source: `api/get-base-schema.md`).
- **AC3**: Given a `baseId` and `tableIdOrName`, When the agent calls `airtable_list_records` with optional `view`, `filterByFormula`, `fields`, `maxRecords`, `pageSize`, `sort`, and `offset`, Then matching records are returned with an `offset` for the next page when more records exist, and `pageSize` above the tool's own ceiling is rejected before any call to Airtable is made.
- **AC4**: Given a `recordId`, When the agent calls `airtable_get_record`, Then that record's `id`, `createdTime`, and `fields` are returned, or a `not_found` error if the record does not exist.
- **AC5**: Given 1–10 field-sets, When the agent calls `airtable_create_records`, Then up to 10 new records are created in one Airtable call and their `id`/`createdTime`/`fields` are returned; more than 10 field-sets is rejected by the tool before calling Airtable; a `partialSuccess` detail in Airtable's response (e.g. an attachment failed to upload) is surfaced to the caller as a non-fatal warning alongside the created records, not swallowed.
- **AC6**: Given 1–10 `{id, fields}` pairs, When the agent calls `airtable_update_records`, Then only the given fields on those records change (other fields are untouched) and the updated records are returned; if the batch contains an id Airtable rejects, the tool surfaces Airtable's error rather than guessing which records applied.
- **AC7**: Given 1–10 explicit record ids, When the agent calls `airtable_delete_records`, Then exactly those records are deleted and the response lists `{id, deleted: true}` per record; the tool has no `filterByFormula`/query parameter — it never accepts anything other than explicit ids for a delete.
- **AC8**: Given a request has no `X-Airtable-Api-Key` header, When any tool is called, Then the response is a structured `unauthorized`/`not_configured` error naming the missing header, and no outbound call is made to Airtable.
- **AC9**: Given Airtable responds with 401/403/404/422/429/5xx, When any tool is called, Then the MCP server maps it into the service's structured error envelope `{"error":{"code","message","retryable"}}` — 404 → `not_found`, 401/403 → `unauthorized`, 422 → `invalid_argument`, 429 → `rate_limited`/`retryable:true` (Airtable: 5 req/s per base, 429 body says wait 30s before retrying — source: `api/errors.md`, `api/rate-limits.md`), 5xx → `upstream_error`/`retryable:true` — without inventing a different status or silently retrying past the tool's own time budget.
- **AC10**: Given two concurrent requests from different tenants carry different credential headers, When both call tools at the same time, Then neither request can read or use the other's credential, and neither can see the other's Airtable data (request-scoped isolation, no cross-request cache).
- **AC11**: Given the server logs a request (including a request with an invalid or missing credential), When the logs are inspected, Then the raw credential value never appears in logs, error bodies, or stack traces.

## Tech design

### Conclusion

Build the first version of `airtable-mcp` from scratch (nothing to modify — the repo is an empty scaffold) following the `vendor-mcp-development` SOP's main line A: Python 3.12 + `uv` + FastMCP, Streamable HTTP, stateless, credential read from a single request header and forwarded to Airtable as `Authorization: Bearer <token>`. Seven tools cover bases/schema discovery plus record CRUD; everything else Airtable's API offers (comments, webhooks, schema writes, enterprise/admin) is explicitly out of scope for v1 (see Non-goals). This is the "most natural" shape: Airtable's REST API already maps one-to-one onto a small set of agent-facing capabilities, so there is no real alternative architecture to weigh beyond "call the REST API directly" vs. "wrap a vendor SDK" (Option analysis, below).

### Where the current implementation lives

None. `README.md:1-2` is the only file in the repo at `e1ce41c`. There is no prior Airtable tooling anywhere in MSPbotsAIFramework to extend (confirmed: `mbp.py project track`/`mcplock info` only found this one repo for the product).

Nearest sibling implementations to mirror the shape of (per `legs/design.md` S2 point 4 — "find the nearest same-kind implementation"): other single-credential, Header-based vendor MCPs built under the same SOP (e.g. the `pax8-mcp`, `ms-graph-mcp` family referenced in `references/mcp-track.md`/project memory as prior MSPbotsAIFramework MCP builds). Those repos were not opened for this design (read-only access to them was not needed to apply the SOP, which is itself the shared template); if the dev leg wants concrete file-layout precedent, `vendor-mcp-development/SKILL.md` §A3 is the authoritative structure to copy, not another vendor's repo.

### Option analysis

| Option | What it does | Pros | Cost | Verdict |
|---|---|---|---|---|
| Call Airtable's REST API directly via `httpx` | Thin async client built to the public OpenAPI-documented endpoints | Full control over header handling (per-request credential, no client-level auth state — required by the SOP's "no shared auth state" rule), full control over error-envelope mapping, no extra dependency surface beyond what every other MCP repo already carries (`httpx`, `fastmcp`, `pydantic-settings`) | Hand-write the 7 endpoint calls (small: list/get/create/update/delete over one resource family) | **Chosen** |
| Wrap a community Airtable SDK (e.g. `pyairtable`) | Use a third-party Python client for request/retry/pagination plumbing | Less boilerplate for pagination/retry | `pyairtable`'s client is built around a single long-lived API key per client instance — using it correctly per-request (new client per call, no reuse of its internal session across tenants) negates most of the convenience, and it is an **open-source third-party package that would become a runtime dependency**, not just a reference; SOP explicitly says open-source MCP/vendor repos are reference-only, clean-room implement against the vendor's own docs | Rejected — convenience doesn't offset taking on a dependency whose statefulness fights the per-request isolation requirement |
| Build v1 with Airtable's official `airtable.js` (Node) instead of Python | Official client, actively maintained | — | Every other MSPbotsAIFramework MCP repo this design was modeled after uses Python 3.12 + uv + FastMCP (the SOP's §9 recommended structure); switching stacks for one vendor adds an inconsistent maintenance surface for no functional gain (Airtable's API has no Node-specific feature) | Rejected — no advantage, breaks stack consistency |

Selection order followed: reuse (nothing in this org to reuse — confirmed empty), open source (considered and rejected, see row 2), self-built thin client (chosen).

### Data & API contract

**Credential header** (SOP §3.1 naming: `X-<Vendor>-<Credential>`):

| Header | Required | Meaning |
|---|---|---|
| `X-Airtable-Api-Key` | yes | A bearer-style Airtable credential: a Personal Access Token created at `airtable.com/create/tokens`, or an OAuth access token obtained via `airtable.com/create/oauth` (source: `api/authentication.md`, fetched 2026-11-02). The MCP server does not distinguish the two — both are forwarded unchanged as `Authorization: Bearer <value>` to `api.airtable.com`. |

Missing header → `401` with body `{"error":{"code":"not_configured","message":"missing required header: X-Airtable-Api-Key","retryable":false}}`, **no call made to Airtable** (AC8).

**Tools** (all under `POST /mcp`, `tools/call`):

| Tool | Airtable endpoint | Scope needed | Hint |
|---|---|---|---|
| `airtable_list_bases` | `GET /v0/meta/bases` (`api/list-bases.md`) | `schema.bases:read` | `readOnlyHint` |
| `airtable_list_tables` | `GET /v0/meta/bases/{baseId}/tables` (`api/get-base-schema.md`) | `schema.bases:read` | `readOnlyHint` |
| `airtable_list_records` | `GET /v0/{baseId}/{tableIdOrName}` (`api/list-records.md`) | `data.records:read` | `readOnlyHint` |
| `airtable_get_record` | `GET /v0/{baseId}/{tableIdOrName}/{recordId}` | `data.records:read` | `readOnlyHint` |
| `airtable_create_records` | `POST /v0/{baseId}/{tableIdOrName}` (`api/create-records.md`) | `data.records:write` | — |
| `airtable_update_records` | `PATCH /v0/{baseId}/{tableIdOrName}` (`api/update-multiple-records.md`) | `data.records:write` | — |
| `airtable_delete_records` | `DELETE /v0/{baseId}/{tableIdOrName}?records[]=...` (`api/delete-multiple-records.md`) | `data.records:write` | `destructiveHint`, `idempotentHint` |

Example — `airtable_list_records` request/response (per AC3):

```json
// tool call arguments
{"baseId": "appXXXXXXXXXXXXXX", "tableIdOrName": "tblYYYYYYYYYYYYYY",
 "view": "Grid view", "maxRecords": 50, "pageSize": 50}

// tool result (compact JSON string)
{"records":[{"id":"rec560UJdUtocSouk","createdTime":"2022-09-12T21:03:48.000Z",
  "fields":{"Name":"Union Square","Address":"333 Post St","Visited":true}}],
 "offset":null}
```

Example — error envelope (AC9, Airtable 429):

```json
{"error":{"code":"rate_limited",
  "message":"Airtable: rate limit exceeded (5 req/s per base); retry after 30s",
  "retryable":true}}
```

Error-code mapping table (AC9, source: `api/errors.md`, fetched 2026-11-02):

| Airtable status / `error.type` | Our `code` | `retryable` |
|---|---|---|
| (no header on our side) | `not_configured` | false |
| 401 (missing/invalid credential) | `unauthorized` | false |
| 403 `INVALID_PERMISSIONS*` | `unauthorized` | false |
| 404 `NOT_FOUND` | `not_found` | false |
| 422 (validation) | `invalid_argument` | false |
| 429 (rate limit) | `rate_limited` | true |
| 500/502/503 | `upstream_error` | true |

**DB**: none — this service has no database; it is a stateless pass-through to Airtable's API.

**Backward compatibility**: first version, nothing to break. Future changes to tool names/required params must follow the SOP §13 breaking-change rules (not this ticket's concern).

### Key flow / sequence

```
Agent -> Gateway -> MCP service (this repo) -> api.airtable.com
1. Gateway calls POST /mcp with X-Airtable-Api-Key and a tools/call body.
2. middleware.py reads the header; missing -> 401 (AC8), done, no outbound call.
   Present -> stores it in a ContextVar scoped to this request.
3. tools.py handler builds the Airtable request from typed tool arguments,
   reads the credential from the ContextVar, calls client.py.
4. client.py sends the HTTPS request to api.airtable.com with
   Authorization: Bearer <token>; on 429/5xx, retries with backoff honoring
   Retry-After, bounded so the whole call stays under the SOP's <120s budget.
5. errors.py maps any non-2xx Airtable response to the structured envelope (AC9).
6. middleware.py resets the ContextVar in a `finally` regardless of outcome (AC10).
7. Result (or error envelope) is serialized compactly and returned as the
   tool's string result.
```

### Non-functional

- **Idempotency & concurrency**: credential lives only in a `contextvars.ContextVar`, set at request start and `reset()` in `finally` — never a module-level/global variable (SOP §3.3/§3.4, AC10). The shared `httpx.AsyncClient` provides connection pooling only; it carries no default `Authorization` header, so concurrent requests from different tenants cannot leak credentials through client state. `airtable_delete_records`/`airtable_update_records` are naturally idempotent on retry (same ids, same intended end state); `airtable_create_records` is not idempotent (repeated calls create duplicate records) — this is Airtable's own semantics, not something this service can paper over, and is documented in the tool description per SOP §A4 (`idempotentHint` only on delete/update, not create).
- **Performance**: connect timeout 5s, read timeout 30s (SOP §5 recommendation); `airtable_list_records` defaults `pageSize` to 50 (not Airtable's own max of 100) to keep single responses token-economical per SOP §A4, caller can raise it up to Airtable's documented ceiling of 100 (`api/list-records.md`) — above 100 is rejected by the tool before calling Airtable (AC3). Responses are capped the same way every other tool in this org is: compact JSON, no pretty-printing, only the fields Airtable returned (no added decoration).
- **Security**: credential read only from the `X-Airtable-Api-Key` header, forwarded over HTTPS, never written to disk, environment, or logs (AC11); `airtable_delete_records` only accepts an explicit list of record ids — there is no formula/filter-based bulk delete, so a single tool call cannot be used to wipe an unbounded set of records (SOP §A4 "write/destructive tools ... not accept ambiguous bulk deletion"); `gitleaks detect` run before delivery (no real credentials ever committed — examples use placeholders).
- **Multi-tenant isolation**: every field that could carry tenant data (records, schema, base list) is request-scoped; nothing is cached across requests or tenants. This is the platform's core multi-tenancy requirement for every MCP service, not something specific to Airtable, and it is enforced structurally (ContextVar + no module-level state) rather than by convention.
- **Observability**: log method, path, Airtable HTTP status, duration, and record counts (not field contents — cell values can be a tenant's business data and should not be logged any more than necessary); never log header values, raw tokens, or full request/response bodies.

### Risks & dependencies

- **Airtable's rate limit (5 req/s per base, documented in `api/errors.md`/`api/rate-limits.md`) could throttle an agent composing several tool calls in a row.** Mitigated by the retry/backoff in `client.py`; surfaced to the caller as `retryable: true` rather than hidden.
- **Self-imposed 10-record batch cap is not a documented Airtable limit** (checked and not found in the fetched create/update/delete docs, 2026-11-02) — if real-world testing (TC-ATB-019) or a future ticket shows Airtable enforces something different, only the shared batch-size constant changes.
- **No Airtable test account available.** Per the SOP, this does not block design, dev, or the INT publish gate; it only means TC-ATB-019 (the one test that needs a live base) stays "needs a real vendor account" until someone provides one. No other ticket or repo is depended on.
- **`partialSuccess` on create/update (Airtable's own documented response shape) must not be silently treated as full success** — covered by AC5 and a dedicated consideration in the create-records test; missing this would surface as "record created" to an agent when, e.g., an attachment actually failed to upload.

- **Scope limited to schema discovery (read) + record CRUD** (7 tools). Skipped: record comments, webhooks, schema writes, attachment-upload-specific flows, enterprise/admin scopes, the Sync API. Why: the ticket only says "give live access" with no named capability; these seven tools are the data operations any generic agent integration needs first. Alternative considered: also expose webhooks for push-style notifications — rejected for v1 because webhooks require a durable subscription/callback target that doesn't fit this service's stateless, per-request design, and nothing in the ticket asks for it.
- **Single credential header (`X-Airtable-Api-Key`) accepts either a Personal Access Token or an externally-obtained OAuth access token**, forwarded unchanged as a bearer token. The server does not implement the OAuth authorization-code exchange itself. Why: this matches the only credential shape `/api/vendor-register` supports ("only supports plain vendors keyed by fixed-key headers... does not need OAuth"); an OAuth consent flow inside a stateless per-tenant MCP service is a different, heavier feature nothing in the ticket asks for. Alternative considered: implement the OAuth flow — rejected, out of scope and unsupported by the registration API.
- **`airtable_list_records` defaults `pageSize` to 50, not Airtable's own default/max of 100.** Why: token economy for the calling agent (SOP §A4 guidance), while still letting a caller explicitly ask for up to 100. Alternative: default to Airtable's 100 — rejected as needlessly large for the common case.
- **Write tools (`create`/`update`/`delete`) are capped at 10 records per call, rejected client-side (before calling Airtable) above that.** This is **not** a documented Airtable limit (see Risks) — it is DEV01's own bound, chosen to keep each call's payload/latency small and to match the common "10 records per batch" convention seen in third-party Airtable clients. Alternative: no cap, forward whatever the agent sends — rejected because an unbounded batch risks large payloads and makes a single tool call's failure mode (partial success, see AC5) harder to reason about.
- **`airtable_delete_records` only accepts an explicit array of record ids — no formula/filter-based bulk delete.** Why: SOP §A4 requires destructive tools to "accept only explicit resource ids, not ambiguous bulk deletion"; Airtable's own delete endpoint is already id-based, so this is a direct mapping, not an added restriction.
